## 1. What each capture confirmed / refuted / returned-negative

### P8 — the LIVE ASK / APPROVAL wire record (freeze row 5) — CONFIRMED, with a structural negative on the recon's primary recipe

This is the round's most consequential result and it overturns the recon's working assumption. **In plain headless `-p` there is NO live ask.** With no permission responder registered, the engine resolves every permission decision internally and either **auto-allows** (a benign input executes) or **auto-denies** (a compound Bash command with a file redirect returns an `is_error:true` `tool_result` reading "the following parts require approval…"). The recon's AVENUE (b) — that a bare stream-json control channel, even with a hand-rolled `{subtype:"initialize"}` handshake and stdin held open, would emit a `can_use_tool` `control_request` — is a **structural negative**: the harness never sends the outward ask unless an SDK `canUseTool` callback (or a `--permission-prompt-tool`) is actually registered in the init handshake. `--permission-mode default` is **necessary but not sufficient**; a registered responder is the missing half. *(P8)*

The live ask **was** captured, via AVENUE (a) — standing up a throwaway stdio MCP tool and routing approval to it with `--permission-prompt-tool mcp__<server>__<tool>`. What that tool receives **is** the ask, delivered as a JSON-RPC `tools/call`. Concrete shapes the adapter can rely on: *(P8)*

- **The prompt-tool ask payload** (`tools/call` arguments): key set `{tool_name, input, tool_use_id}` — `tool_name` is the tool requesting permission (e.g. `Bash`), `input` is that tool's full input object, `tool_use_id` is the correlation/prompt id. A sibling `_meta` carries `{claudecode/toolUseId, progressToken}` where `claudecode/toolUseId` equals `tool_use_id`. Both key sets were stable across two runs. *(P8)*
- **The option set.** The allow-once / allow-always / reject choice surfaces as a `decisionClassification` enum with exactly three members: `user_temporary` (allow-once), `user_permanent` (allow-always), `user_reject` (reject). The responder answers with `behavior: "allow" | "deny"` — **allow** returns `updatedInput` (the echoed-or-rewritten tool input) plus optional `updatedPermissions`; **deny** returns a `message` plus optional `interrupt`. *(P8)*
- **The single correlation key is `tool_use_id`.** It threads ask → `assistant` `tool_use.id` → `user` `tool_result.tool_use_id` → `result.permission_denials[].tool_use_id`, verified identical end-to-end on both the deny and the allow path. On answered-deny the `message` propagates verbatim into the `is_error:true` `tool_result` **and** into `result.permission_denials[]`; on answered-allow the tool actually executes (`is_error:false`) and `permission_denials` is empty. *(P8)*
- **The native control-channel ask** (the shape the adapter will see when it acts as a real SDK host, extracted from the binary, not observed live in `-p`): `control_request{request_id, request:{subtype:"can_use_tool", tool_name, display_name, input, description?, permission_suggestions[], blocked_path?, decision_reason, decision_reason_type, classifier_approvable, tool_use_id, agent_id}}`, answered by `control_response{response:{subtype:"success", request_id, response:{behavior, updatedInput?, updatedPermissions?, message?}}}`, with cancel via `control_cancel_request{request_id}`. The richer fields (`display_name`, `permission_suggestions[]`, `classifier_approvable`, `agent_id`, `decision_reason*`) appear **only** on this native channel and are **not** delivered to the prompt-tool form — the two are semantically the same ask, but the prompt-tool route cannot source the structured suggestion list. *(P8)*
- **Pending / answered / timeout / parked state for re-attach** lives in the `initialize` `control_response`, which carries `pending_permission_requests[]` (and `pending_user_dialog_requests[]`) so a re-attaching client re-arms in-flight/parked asks. There is **no separate socket-hold field** — the "hold" is simply the open `control_request` awaiting its `control_response`; user-dialog asks honor `CLAUDE_CODE_USER_DIALOG_TIMEOUT_MS` and resolve as `{behavior:"cancelled"}` on timeout. *(P8)*

**Adapter rule this establishes:** the `attach.v1` ask event MUST be sourced from the control protocol, never from headless `-p` stdout. The adapter has exactly two ways to receive it — act as an SDK host on the stream-json control channel and register a `canUseTool` responder, or register a `--permission-prompt-tool` MCP tool — and prefer the native channel when it needs the structured `permission_suggestions[]`. Map the ask's request id to `tool_use_id`; map the option set to `behavior` × `decisionClassification`; source pending/answered/timeout from the `initialize` response's `pending_permission_requests[]`. This directly resolves the PHASE2 §3 "the ask/denial event is currently un-sourceable" gap. *(P8)*

### P9 — SESSION-STATE wire vocabulary (freeze row 3) — PARTIAL (Layer-1 enumerated; Layer-2 deferred)

P9 enumerated the value sets that the §3 mapping switches on, in Layer-1 print mode. *(P9)*

- **`system/status`** is a fixed 5-key record `{type, subtype, status, uuid, session_id}`; `subtype` is always the literal `"status"`. Its `.status` value set in print mode is **`{requesting}` only** — emitted once per model API round-trip (a two-round-trip tool-use turn produces two pings). Across 23 status pings (mine + a parallel session) **no** `busy`/`idle`/`working`/`compacting` value ever appeared. These richer states are very likely TUI/Layer-2-only; reported as **unobserved, not refuted**. So the `system/status` channel is a thin "a request is in flight" signal, not a state enum. *(P9)*
- **`result`** is the terminal record; its key set differs by outcome — `success` carries `terminal_reason` and no `errors[]`; budget/turns terminals carry `errors[]` (free text) and `is_error:true`, with budget **dropping** `terminal_reason` while max-turns **keeps** it. Observed cross-tab: `success` → `stop_reason=end_turn`, `terminal_reason=completed`, `is_error=false`; `error_max_budget_usd` → `stop_reason ∈ {tool_use, end_turn}`, `terminal_reason` **absent**, `is_error=true`; `error_max_turns` → `stop_reason=tool_use`, `terminal_reason=max_turns`, `is_error=true`. The observed value sets: `result.subtype ∈ {success, error_max_budget_usd, error_max_turns}`; `result.stop_reason ∈ {end_turn, tool_use}`; `result.terminal_reason ∈ {completed, max_turns, ABSENT-on-budget}`. *(P9; P13 widens the subtype set — see below)*
- **Background-task lifecycle is the real WORKING signal**, carried by three system subtypes. `system/task_started` (keys diverge by `.task_type`: `local_agent` adds `prompt`+`subagent_type`, `local_bash` omits them; `.task_type ∈ {local_agent, local_bash}`) → `system/task_progress` (in-flight ping; keys include `last_tool_name`, `subagent_type`, `usage{total_tokens,tool_uses,duration_ms}`; **carries no `.status` field**) → `system/task_notification` (terminal; keys `{output_file, status, summary, task_id, tool_use_id, usage}`; `.status` observed value **`{completed}` only**, 24 observations). This lifecycle fires only for backgrounded/slow tools — a quick inline `exit 7` Bash never entered it, so failure/abort `task_notification.status` variants stay unobserved. *(P9)*

**Build-version finding:** this build (`2.1.173`) has **no `--max-turns` flag in print mode** (verified against the full `claude -p --help` dump). The `error_max_turns` / `terminal_reason=max_turns` terminal is real on this same build but is only reachable via `--input-format stream-json` (which enforces a per-call turn cap); the corroborating capture came from a parallel operator session, not the print recipe. *(P9)*

**Adapter rule this establishes:** detect WORKING from `system/status.status=requesting` **OR** any open `task_*` (a `task_started`/`task_progress` with no matching `task_notification`); return to ATTACHED on a `result` with no open tasks. Branch terminal classification on `result.subtype` + `is_error`, **never** on `stop_reason` (non-deterministic between `tool_use`/`end_turn` on the budget terminal), and treat `terminal_reason` as optional (dropped on budget). Do not expect a richer status enum from the print stream. *(P9)*

### P14 — MCP / Skill / plugin tool framing — CONFIRMED, the discriminator is name+input, never block keys

P14 settles how the adapter tells a namespaced MCP tool, a Skill, and a subagent spawn apart — the PHASE2 §2 concern that the adapter "must not misclassify a namespaced MCP tool as a subagent spawn." The whole game is that `system/init` carries **two disjoint registries**: `init.tools[]` (a flat array of callable tool names, native + `mcp__*`) and `init.agents[]` (a flat array of subagent *types*, e.g. `claude`/`Explore`/`general-purpose`/`Plan`/`statusline-setup`). MCP tools live in the first; subagents live in the second; the arrays never overlap. `init.skills[]` and `init.slash_commands[]` are separate string arrays (every skill name also appears as a slash command, which is a superset adding built-ins); `init.plugins[]` was empty in this environment. *(P14)*

The critical confirmation: the **`tool_use` block top-level key set is IDENTICAL** across MCP, Agent, Skill, and native — `{type, id, name, input, caller}` with `caller=={type:"direct"}` in every case. **Discrimination is on `name` + `input` shape only**: *(P14)*

- **MCP tool** → `name` matches `^mcp__<server>__<tool>`; `input` is the tool's own schema (e.g. `{text}`). Namespacing is literally `mcp__` + the sanitized server config KEY (spaces/dots → `_`, e.g. `claude.ai Gmail` → `claude_ai_Gmail`) + `__` + tool name. **Decompose with `split("__")` (double underscore) → ≥3 parts**; a single-underscore split is WRONG because tool names contain single underscores (`complete_authentication`). Confirmed live: `mcp__echotest__echo`, `input={text:"ds-ping"}`, `tool_result` content `[{type:"text", text:"ECHO: ds-ping"}]`. *(P14)*
- **Subagent spawn** → `name ∈ {Agent, Task, TaskCreate}` (sonnet emits `Agent` reliably; the haiku `Task`→`TaskCreate` misfire from the boundary-harness note still applies); the discriminator is `input.subagent_type`, whose value is in `init.agents[]`. *(P14, consistent with PHASE2 P1)*
- **Skill** → native `name=="Skill"`, `input={skill}` whose value is in `init.skills[]`. NOT a slash-command record, NOT an `mcp__` tool, NOT an Agent. *(P14)*

**Adapter rule this establishes:** classify `tool_use` by `name`, in order — `^mcp__…` (split on `__`, server=part 1, tool=join of the rest) ⇒ MCP; `name ∈ {Agent, Task, TaskCreate}` ⇒ subagent (read `input.subagent_type`); `name=="Skill"` ⇒ skill (read `input.skill`); otherwise native. **Never** classify on the block key set or `caller.type` (identical across all four). Build the subagent-type allowlist from `init.agents[]` and the skill allowlist from `init.skills[]`. Expect a **deferred-tool hop**: a freshly-wired MCP tool may require a `ToolSearch` `tool_use` first, whose `tool_result` content carries a **new subtype `tool_reference` `{tool_name}`** — tolerate it preceding the first real `mcp__` call. Surface `needs-auth` MCP servers' `*__authenticate`/`*__complete_authentication` tools as gated (they are injected into `init.tools[]` regardless of `--tools`/`--allowedTools`), never auto-invoke them. *(P14)*

### P13 — `result.subtype` error variants + `is_error:true` `tool_result` body — CONFIRMED, closes the closed set

P13 enumerates the closed set PHASE2 §2 flagged as unenumerated. **`result.subtype` closed set = `{success, error_during_execution, error_max_turns, error_max_budget_usd, error_max_structured_output_retries}`.** Accompanying-field rules: `error_max_budget_usd` → `is_error:true`, no `result`, no `terminal_reason`, no `api_error_status`, adds `errors[]`, exit 1; `error_max_turns` → `is_error:true`, `terminal_reason=max_turns`, no `result`, no `api_error_status`, adds `errors[]`, exit 1; **`api_error_status` is present only when `subtype==success`.** On the body shape: an `is_error:true` `tool_result` content is a **bare string** (block keys `{content, is_error, tool_use_id, type}`), and the sibling `tool_use_result` is a bare `Error: …` string on failure versus a structured object on success. A denial **keeps `subtype==success`** but populates `permission_denials[]` and emits an `is_error:true` `tool_result` — consistent with P8. *(P13)*

**Adapter rule this establishes:** switch on the closed `result.subtype` set, treat `terminal_reason`/`api_error_status` as subtype-conditional (present only where noted), and parse `is_error:true` `tool_result` content as a bare string (not an array). This closes the PHASE2 P12/P13 "error-shaped body unobserved" gap.

### P11 — `--include-partial-messages` `stream_event` assembly contract — CONFIRMED

P11 documents the partial-stream reassembly contract (PHASE2 §2's P11 ask). A partial assistant turn is bracketed by a `stream_event` envelope emitting, in strict order, `message_start` → (`content_block_start` → `content_block_delta`* → `content_block_stop`)* → `message_delta` → `message_stop`. Each top-level `stream_event` carries `{event, parent_tool_use_id, session_id, type, uuid}` (+ `ttft_ms` only on `message_start`). The delta types: `text_delta`→text, `thinking_delta`→thinking, `signature_delta` (terminal for a thinking block), and **`input_json_delta`→a tool_use block's input streamed incrementally**. *(P11)*

The reassembly rule: open a buffer per `event.index` on `content_block_start`, coalesce deltas by concatenation until `content_block_stop`, and for `input_json_delta` concatenate `partial_json` and **only then `JSON.parse`** — the first `input_json_delta` is an empty-string priming delta and intermediate concatenations are invalid JSON by design. Verified byte-exact in two runs that the concatenation equals the non-partial record's `.input`. Authoritative `stop_reason` and final usage come from `message_delta`, not `message_start` (whose usage is a prefix snapshot). *(P11)*

Two structural truths the adapter must honor: **(a) the non-partial records are authoritative** — the CLI emits the fully-reassembled non-partial `assistant`/`user`/`result` records on the same stream, and the partial deltas are a **duplicate for live rendering only**; the adapter should build canonical state from non-partial records and use partials purely for incremental UI. **(b) The non-partial `assistant` record is emitted once PER CONTENT BLOCK, not once per message** — a 2-block message (thinking+tool_use) yields two `assistant` records sharing one `message.id`; merge by `message.id`. Non-`stream_event` records (the non-partial `assistant`, `user`, `system/*`) can interleave **mid-envelope** (observed between a block's last delta and its `content_block_stop`), and the `user` `tool_result` position relative to the envelope close is **nondeterministic** — anchor on `content_block_stop`/`message_stop`, never on `tool_result` position. *(P11)*

**Adapter rule this establishes:** treat `stream_event` as a render channel only; reassemble per `event.index` within an envelope and flush on `content_block_stop`; parse `input_json_delta` only at stop; merge per-block non-partial `assistant` records by `message.id`; tolerate non-`stream_event` records mid-envelope; carry `parent_tool_use_id` through for future subagent support. *(P11)*

### P10 — ordering / sequence evidence (freeze row 1, projection-resume) — CONFIRMED: stdout arrival order is a SAFE basis

P10 is the verdict the projection-resume row needs. **There is no monotonic wire sequence number** — an exhaustive scan for `seq|sequence|index|offset|counter|ordinal|position|monotonic|tick|lsn` across four raw runs found only `event.index`, which is **per-message and resets to 0 at each `message_start`**, so it cannot order records across messages or across the spawn/complete split; all `uuid`s are random v4 and carry no order. *(P10)*

The load-bearing evidence is an **asymmetric-latency** fan-out (three subagents, alpha given a long deliberation): **spawn-side records interleave in spawn order** (the `Agent` `tool_use` and `system/task_started` lines arrive alpha→bravo→charlie) while **completion-side records arrive in completion order** (`task_notification` and the `user` `tool_result` arrived bravo→charlie→alpha, the heavy alpha last). Crucially, **causal happens-before always holds in stdout arrival order**: for every subagent, its `task_started` precedes its `task_notification` even when completions reorder — so stdout order is a valid **topological sort of the spawn→complete DAG**. Two base fan-out runs were diffed and had identical type:subtype key-set signatures (model-nondeterminism narration aside). *(P10)*

A clean negative resolves the PHASE2 "do deltas straddle their parent?" question: with `--include-partial-messages`, **subagent token-level deltas do NOT stream to parent stdout** — all 40 `stream_event` records carried `parent_tool_use_id == null/ROOT`; none nested under a subagent's `toolu_*`. Subagent activity surfaces only via `task_started`/intermediate `user`/`task_notification`/`tool_result`. (Non-`stream_event` records *do* straddle the parent envelope, consistent with P11.) *(P10)*

**Adapter rule this establishes:** synthesize the `attach.v1` `seq` from stdout line-arrival order (a per-record monotonic counter) — it is causally safe because the single-process local CLI serializes all records onto one stdout fd and that serialization respects per-task happens-before. Do **not** derive order from `uuid`, `task_id` (both random/opaque), or `event.index` (per-message, resets). Correlate the subagent lifecycle on the single join key `tool_use_id`, maintaining separate spawn-order and completion-order projections off it and matching by id, never by position. The guarantee the adapter may assume is exactly "single-writer stdout serialization respecting per-task happens-before" and **nothing stronger** (no global wire sequence, no cross-task ordering beyond arrival). *(P10)*

## 2. CC-status → `attach.v1` §3 state-machine mapping (from P9)

The §3 chain (doc 15 §3): PENDING → CREATING → READY → ATTACHED ⇄ WORKING; SNAPSHOTTING/SUSPENDED/PARKED branch off. The honest result is that **only ATTACHED and WORKING have a clean CC-wire source**; everything else is orchestrator-owned and the adapter must **not** try to infer it from the stream.

| §3 state | CC wire source | Mapping |
|---|---|---|
| PENDING | **none** — pre-spawn, orchestrator-side (request queued, no CC process yet) | no CC source |
| CREATING | **none** — orchestrator-side (VM/boundary bring-up; D72/D73 READY gates). `system/init` is the earliest CC signal and marks the CREATING→READY/ATTACHED handoff, but CREATING itself is orchestrator-owned | no CC source |
| READY | **none directly** — `system/init` arrival is *evidence* the CC process is live and idle, not the gate (READY is gated on D72/D73 applied_seq + digest-ack) | `init` = readiness evidence only |
| ATTACHED | between turns: after a `result` (terminal) and before the next `system/status:requesting`; also the idle steady-state after `init` | `result` received AND no in-flight task ⇒ ATTACHED (run-loop idle) |
| WORKING | `system/status.status=requesting` (model call in flight) AND/OR any open `task_*` (a `task_started`/`task_progress` with no matching `task_notification`); a `thinking_tokens` stream also implies WORKING | requesting-ping OR open `task_*` ⇒ WORKING; ATTACHED⇄WORKING toggles on requesting-ping / `result` boundaries |
| SNAPSHOTTING | **none** — orchestrator-side (CRIU/snapshot on >15 min pause or migrate, D46); the VM keeps emitting WORKING on the wire | no CC source |
| SUSPENDED(reason: user \| policy_breach \| rebalance) | **none** — D77: VM suspend is reserved for genuine threats; the 30–60 s socket-hold is explicitly **not** a VM state (§3 refinement 4); the VM stays WORKING on the wire | no CC source |
| PARKED | **none** — orchestrator/scheduler-side (host slot released, re-place via CREATING@host′); free-metering pause on D46 >15 min / unanswered rung-2 ask | no CC source |

CC terminals (`result`) do **not** drive §3 transitions directly: `result/success` returns the loop to ATTACHED; a non-success `result` (`error_max_budget_usd`/`error_max_turns`) ends the CC turn but the §3 session can stay ATTACHED for a new turn — the terminal is **per-invocation, not per-session**, and the orchestrator decides whether to re-drive. The Layer-2 status vocabulary (`claude agents --json` → `{pid,cwd,kind,sessionId,status}`) was **not** run this round (Layer-1-only constraint), so this mapping is built purely from the Layer-1 stream — the candidate richer statuses (idle/compacting) that might fill READY-evidence or a quiesced state remain a Layer-2 follow-up. *(P9)*

## 3. Load-bearing implications + FREEZE-ROW STATUS update

### For the `dreamserpent.attach.v1` event model (D18 / D38)

- **The ask event is now sourced** (row 5). It does not come from headless `-p` stdout — the adapter must be an SDK host with a `canUseTool` responder (native control channel, the richer shape) or register a `--permission-prompt-tool` (the prompt-tool shape). Socket-hold visibility is the open `control_request` itself, carried as ask-event payload (exactly as §6.1 row 5 demands: "socket-hold visibility carried as ask-event payload, never state vocabulary"), with pending/answered/timeout coming from the `initialize` response's `pending_permission_requests[]`. *(P8)*
- **The CC→§3 mapping is no longer a guess** (row 3) but is *honestly partial*: only ATTACHED⇄WORKING have a CC-wire source; PENDING/CREATING/SNAPSHOTTING/SUSPENDED/PARKED are orchestrator-driven via `WatchSession`, and READY is gated with `init` as evidence only. The adapter must not synthesize the orchestrator-owned states from the stream. *(P9)*
- **Sequencing is now verified safe** (row 1). Synthesize `seq` from stdout arrival order; it is a topological sort of the spawn→complete DAG under single-writer serialization. This removes the PHASE2 "unverified causal-ordering assumption" caveat for the **local Layer-1 single-process** case (a Layer-2 daemon multiplexer is explicitly out of scope and could break the single-writer guarantee). *(P10)*
- **Tool classification is name-driven** (supports row 4 and the canvas tile fields). The adapter classifies MCP/subagent/Skill/native by `name`+`input`, never by block keys — so a namespaced MCP tool can never be mistaken for an `Agent` spawn. *(P14)*

## 4. Negative results & uncertainties

**Confirmed negatives:**
- **P8 — AVENUE (b) is a structural negative.** A bare stream-json control channel in headless `-p` does NOT emit a `can_use_tool` `control_request`; with no responder registered the engine auto-allows or auto-denies internally. `--permission-mode default` alone is insufficient; a registered `canUseTool` callback OR `--permission-prompt-tool` is required. The binary corroborates: "canUseTool callback cannot be used with permissionPromptToolName" and "canUseTool callback is not provided." This **corrects the recon's primary recipe assumption.** *(P8)*
- **P8 — the `--permission-prompt-tool` literal `stdio` value** is accepted but does NOT surface a live ask for benign Bash (auto-executes); only the `mcp__server__tool` form is a reliable capture route. *(P8)*
- **P8 — `system/permission_denied`** is NOT always emitted on a denial: the Bash "multiple operations require approval" path returns an `is_error` `tool_result` directly rather than going through the `createCanUseTool` deny short-circuit that enqueues the event. Adapters must not rely on `system/permission_denied` always accompanying a denial. *(P8)*
- **P9 — no `--max-turns` in print mode** on `2.1.173`; `error_max_turns`/`terminal_reason=max_turns` is only reachable via `--input-format stream-json`. The print recipe cannot enforce a turn cap. *(P9)*
- **P9 — `system/status.status` emitted only `requesting`** across 23 pings; `busy`/`idle`/`working`/`compacting` were never seen (reported unobserved, not refuted — likely TUI/Layer-2-only). *(P9)*
- **P10 — subagent token deltas do NOT stream to parent stdout** (all `stream_event` `parent_tool_use_id == null/ROOT`); subagent internals surface only via `task_*`/`user`/`tool_result`. **No monotonic wire sequence number exists.** *(P10)*
- **P14 — `caller.type` is NOT a discriminator** (`{type:"direct"}` for MCP/Agent/Skill alike); a namespaced MCP tool never collides with an `Agent` spawn (name is the literal `Agent`, MCP name always `^mcp__`). *(P14)*

**Uncertainties and `n=1`/provenance caveats:**
- **Model nondeterminism on the ask (P8).** Benign Write/Bash-to-`/etc` or `/tmp` requests were sometimes **refused by the model as suspected prompt-injection** (it recognizes this repo's framing) — these are INCONCLUSIVE turns, not negatives. A compound Bash command with a file redirect, framed as legitimate scratch-dir setup, reliably (a) got the model to call the tool and (b) escalated the decision to "ask." Assert structurally on the presence of the ask record + key set, never on model free-text. *(P8)*
- **The native `can_use_tool` wire record was NOT observed live in `-p`** (only its shape, extracted from the binary). The live payload captured is the prompt-tool delivery; the two are semantically equivalent asks but field names differ (the prompt-tool form omits `permission_suggestions`/`blocked_path`/`classifier_approvable`/`agent_id`/`decision_reason*`). The adapter cannot source the structured suggestion list via the prompt-tool route. *(P8)*
- **P9/P13 task-failure and compacting states unobserved.** `task_notification.status` failure/abort variants were not reached (a quick `exit 7` ran inline and never entered the task lifecycle); `compacting` was deliberately not forced (needs a long, costly transcript). These remain open. *(P9)*
- **Provenance — parallel operator sessions.** `error_max_turns` (P9/P13) and the `Agent` subagent-spawn contrast blocks (P14) were corroborated against parallel operator D49-round-3 captures sharing the same job dir (same build `2.1.173`), not freshly re-spawned this round — flagged per the parallel-sessions discipline; the print recipe cannot itself reach `error_max_turns`. *(P9/P14)*
- **P11 subagent nesting untested** — `parent_tool_use_id` was null in both partial-message runs; how child `stream_event` deltas interleave under a spawned subagent is untested here (and P10 shows they do not stream to parent stdout at all). Parallel tool calls within one message (indices 1,2,3…) were not exercised, though the per-index buffering rule generalizes. *(P11)*
- **`n=1`/stability.** Where a finding rests on a single run, assert structurally and diff record-type + key sets before promoting to a rule (the PHASE2 methodology guidance still stands). The P8 ask shape was stable across two runs; the P10 base fan-out was diffed across two runs plus the asymmetric-latency run.

**Hard-constraint compliance.** All captures were Layer-1 `claude -p` only, each carrying `--no-session-persistence`, `--max-budget-usd 0.60` (one `0.01` budget-terminal probe), `--model sonnet`, `--permission-mode default`; raw written only under the job tmp `cap/phase3/` dir; no `/tmp/cc-daemon-<uid>/` socket touched; no `~/.claude/*` edited; throwaway stdio MCP child processes (for P8/P14) were spawned and reaped with the `claude` process. No `sk-ant-*`/`Bearer` secrets were present in or pasted from any capture (`apiKeySource` was `none` on the capture host).

## 5. The secret-scan + fixture-provenance CI gate

All three self-test clauses passed:

- **Clause (i) — no false positives on the current tree → EXIT 0.** Running against the current repo tree exits 0, proving both that the committed cassette `client/fixtures/subagent-spawn.cc-wire.ndjson` has a valid synthetic header and that the redacted placeholders in the goldentrace docs do not trip the scan.
